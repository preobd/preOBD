# Feature cost matrix

What each feature flag and sizing knob actually costs in flash and static RAM,
so a build can be planned for a memory-constrained target *before* compiling
rather than by trial and error. Generated by
[`tools/measure_feature_costs.py`](../../tools/measure_feature_costs.py).

> **Scope:** mega2560, where the budget (8 KB RAM) makes these costs
> decision-relevant, and feather_f405, the STM32F405 that is the v1 PCB candidate
> MCU. Teensy/ESP32 have ample headroom. Other platforms can be added to the
> tool's `ENVS` table if that changes.

## How it's measured

For each knob, the tool toggles it in `boards/mega2560/board.h` relative to the
current baseline, rebuilds, and diffs the ELF:

- **Flash** = `.text + .data`
- **Static RAM** = `.data + .bss` (does *not* include heap or stack)

Regenerate after code changes:

```bash
python3 tools/measure_feature_costs.py --env mega2560
```

> ⚠️ **Clean builds are mandatory.** PlatformIO/SCons does **not** track the
> `-include`d profile header as a build dependency, so an incremental build after
> a profile edit serves a **stale ELF** and reports zero deltas. The tool runs
> `pio run -t clean` before every build for this reason — and any manual
> before/after size comparison must do the same.

## mega2560

> **These figures are out of date.** They were measured before the v0.13.0
> registry change that cut mega2560 flash from 85.6% to 69.0%, so the flash
> baseline below is too high; the RAM picture has changed too: 86.4% after #147/#523, and see the
> stack note below — the old ≈98% figure didn't leave enough stack to boot. Per-flag
> deltas are indicative. Re-run `tools/measure_feature_costs.py` to refresh.

Baseline at the time of measurement: **flash 194,398 B (76.5%)**, **static RAM 8,102 / 8,192 B
(98.9%) — only 90 B of headroom.**

### Per-flag cost

Negative = removing the feature frees that much. Positive = adding it costs that
much (and several would overflow the 90 B RAM headroom — see notes).

| Knob | ΔFlash | ΔStatic RAM | Note |
|---|---|---|---|
| **Currently on** | | | |
| `SUPPORTS_CAN` | −11,568 B | **−691 B** | largest RAM consumer (MCP2515 + frame cache) |
| `SUPPORTS_ALARMS` | −16,426 B | **−455 B** | **gates the whole control engine on AVR** (see below) |
| `INCLUDE_LED` | −2,206 B | −318 B | RGB status indicator (wiring-derived†) |
| `SUPPORTS_LCD` | −4,746 B | −236 B | I²C LCD |
| `SUPPORTS_BME280` | −7,766 B | −174 B | Adafruit BME280 |
| `INCLUDE_MODE_BUTTON` | −808 B | −133 B | wiring-derived† |
| `SUPPORTS_SERIAL_OUTPUT` | −3,170 B | −28 B | cheap RAM, but a core output |
| **Currently off** | | | |
| `SUPPORTS_FRAMED_TRANSPORT` | +5,192 B | **+1,691 B** | would overflow RAM ~19× over; real ceiling |
| `SUPPORTS_ELM327` | +4,202 B | +301 B | would overflow RAM headroom |
| `SUPPORTS_TEST_MODE` | +7,568 B | +238 B | would overflow RAM headroom |
| `SUPPORTS_CLI_EDITING` | ≈ +3.1 KB | **≈ +690 B** | embedded-cli editor; the stack can't spare it (#147, measured 2026-10-01 below) |
| `SUPPORTS_RELAY_OUTPUT` | +1,194 B | +32 B | cheap (deprecated → Actions) |
| `SUPPORTS_REALDASH` | +222 B | +36 B | **nearly free** — disabled by choice, not a RAM limit |
| `INCLUDE_SD_LOGGING` | — | — | won't build: `SD.h` not in mega `lib_deps` (lib + RAM ceiling) |

> † `INCLUDE_LED` / `INCLUDE_MODE_BUTTON` are derived from `wiring.ini` pin presence,
> not `board.h` flags, so the measurement tool (which toggles `board.h`) can't
> re-measure them — values carried from a prior run.

> **Naming:** these were `ENABLE_*` in older releases. `SUPPORTS_*` is the `board.h`
> capability you comment out to reclaim the memory; `INCLUDE_*` is what
> `resolve.h` derives and `src/` tests. Neither means the feature is *on* at
> runtime.

## feather_f405

STM32F405RG (128 KB SRAM + 64 KB CCM, 1 MB flash), every capability declared,
teensy41 sizing (`MAX_INPUTS` 40). Measured 2026-11-01 (#100).

**Baseline:** flash 350,884 B; static RAM 36,512 B of 131,072. That figure is
`arm-none-eabi-size`'s data + bss, which includes the linker script's fixed
1,540 B heap/stack reserve (`._user_heap_stack`), so it is about 1.6 KB above
the RAM PlatformIO reports (34.9 KB). The reserve is the same in every build,
so the deltas below are unaffected. CCM is unused.

**At run time** (`VERSION`'s "min free", which counts heap and stack too):

| Load | Min free |
|---|---|
| RUN, 13 inputs, CAN in+out, nRF framed link, LCD, BME280, MAX31855 (SD logging off) | 82,288 B |
| Worst seen: `LOAD SD:` of a 13 KB config | 53,684 B (41%) |

## Lessons

- **`SUPPORTS_ALARMS` is the control-engine switch on AVR, not a buzzer flag.**
  `INCLUDE_RULES_ENGINE` is `INCLUDE_ALARMS || INCLUDE_RELAY_OUTPUT`
  (`rules_types.h`), so disabling alarms removes the entire Rules/Actions engine
  (−16.4 KB / −455 B — grew with the standalone arena tables). The physical
  buzzer is a separate pin (`BUZZER_PIN`).
- **Static RAM % is not the budget; the stack is.** Measured on hardware
  (2026-10-01, #523) by painting free RAM at reset: boot peaks at 501 B of stack,
  `SAVE` at ~630 B. At 97.4% static RAM (≈210 B left) the board crash-looped
  before printing anything, so keep **≥ ~900 B** free (≲ 89% static). It was
  the embedded-cli editor's 820 B arena that ate the margin: mega now drops
  `SUPPORTS_CLI_EDITING` for a 128 B line reader (#147) and sits at 86.4%,
  with 492 B of stack never touched.
- **PROGMEM must end below 64 KB.** Near `pgm_read_*` only addresses
  0x0000–0xFFFF, so a table or `F()` string above it reads garbage.
  `scripts/avr_progmem_guard.py` fails the build past the line, and
  `boards/avr_pstr_merge.h` lets the linker fold duplicate `F()` strings
  (−9.3 KB, #523). The build prints `PROGMEM: ends at 0x…`: watch that headroom
  as well as flash %.
- **`MAX_INPUTS` is the cleanest scaling knob** (~110 B/input), confirming the
  earlier estimate.
- **Not every disabled feature is a RAM ceiling.** `REALDASH` costs +36 B — it's
  off on mega by *choice*, not necessity. `FRAMED_TRANSPORT` (+1,691 B), `ELM327`
  (+301 B), and `TEST_MODE` (+238 B) are genuine ceilings (each exceeds the 90 B
  headroom); `SD_LOGGING` can't even link without added `lib_deps`.
- **ArduinoJson/SD are flash + heap costs, not static-RAM drivers** — consistent
  with the earlier finding; the static-RAM drivers are the CLI buffers and the
  input array.
