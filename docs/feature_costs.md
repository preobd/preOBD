# Feature cost matrix

What each feature flag and sizing knob actually costs in flash and static RAM,
so a build can be planned for a memory-constrained target *before* compiling
rather than by trial and error. Generated by
[`tools/measure_feature_costs.py`](../tools/measure_feature_costs.py).

> **Scope:** mega2560 only. It's the one target where the budget (8 KB RAM) makes
> these costs decision-relevant — Teensy/ESP32 have ample headroom. Other
> platforms can be added to the tool's `ENVS` table if that changes.

## How it's measured

For each knob, the tool toggles it in `boards/mega2560/board.h` relative to the
current baseline, rebuilds, and diffs the ELF:

- **Flash** = `.text + .data`
- **Static RAM** = `.data + .bss` (does *not* include heap or stack)

Regenerate after code changes:

```bash
python3 tools/measure_feature_costs.py --env mega2560
```

> ⚠️ **Clean builds are mandatory.** PlatformIO/SCons does **not** track the
> `-include`d profile header as a build dependency, so an incremental build after
> a profile edit serves a **stale ELF** and reports zero deltas. The tool runs
> `pio run -t clean` before every build for this reason — and any manual
> before/after size comparison must do the same.

## mega2560

Baseline (post-#296): **flash 194,398 B (76.5%)**, **static RAM 8,102 / 8,192 B
(98.9%) — only 90 B of headroom.**

### Per-flag cost

Negative = removing the feature frees that much. Positive = adding it costs that
much (and several would overflow the 90 B RAM headroom — see notes).

| Knob | ΔFlash | ΔStatic RAM | Note |
|---|---|---|---|
| **Currently on** | | | |
| `SUPPORTS_CAN` | −11,568 B | **−691 B** | largest RAM consumer (MCP2515 + frame cache) |
| `SUPPORTS_ALARMS` | −16,426 B | **−455 B** | **gates the whole control engine on AVR** (see below) |
| `INCLUDE_LED` | −2,206 B | −318 B | RGB status indicator (wiring-derived†) |
| `SUPPORTS_LCD` | −4,746 B | −236 B | I²C LCD |
| `SUPPORTS_BME280` | −7,766 B | −174 B | Adafruit BME280 |
| `INCLUDE_MODE_BUTTON` | −808 B | −133 B | wiring-derived† |
| `SUPPORTS_SERIAL_OUTPUT` | −3,170 B | −28 B | cheap RAM, but a core output |
| **Currently off** | | | |
| `SUPPORTS_FRAMED_TRANSPORT` | +5,192 B | **+1,691 B** | would overflow RAM ~19× over; real ceiling (cf. #233) |
| `SUPPORTS_ELM327` | +4,202 B | +301 B | would overflow RAM headroom |
| `SUPPORTS_TEST_MODE` | +7,568 B | +238 B | would overflow RAM headroom |
| `SUPPORTS_RELAY_OUTPUT` | +1,194 B | +32 B | cheap (deprecated → Actions) |
| `SUPPORTS_REALDASH` | +222 B | +36 B | **nearly free** — disabled by choice, not a RAM limit |
| `INCLUDE_SD_LOGGING` | — | — | won't build: `SD.h` not in mega `lib_deps` (lib + RAM ceiling) |

> † `INCLUDE_LED` / `INCLUDE_MODE_BUTTON` are derived from `wiring.ini` pin presence,
> not `board.h` flags, so the measurement tool (which toggles `board.h`) can't
> re-measure them — values carried from a prior run.

> **Naming:** these were `ENABLE_*` before #357. `SUPPORTS_*` is the `board.h`
> capability you comment out to reclaim the memory; `INCLUDE_*` is what
> `resolve.h` derives and `src/` tests. Neither means the feature is *on* at
> runtime.

### Structural knobs

| Knob | ΔFlash | ΔStatic RAM | Per-unit |
|---|---|---|---|
| `MAX_INPUTS` 8→16 / 8→4 | ~0 | +880 B / −440 B | **≈110 B / input** |
| `CLI_BUFFER_SIZE` 820→512 | −754 B | **−852 B** | single largest RAM lever |
| `CAN_CACHE_SIZE` 8→16 | ~0 | +128 B | 16 B / entry |
| `MAX_PIN_REGISTRY` 24→16 | 0 | −40 B | 5 B / entry |
| `MAX_PID_ENTRIES` 8→16 | 0 | +24 B | 3 B / entry |

| Symbol | Bytes |
|---|---|

> Since #296 the control-engine Rule/Action tables are standalone globals
> (`rules` 42 B + `actions` 12 B + `g_ruleContexts` 26 B at the AVR cap of 2),
> no longer part of `systemConfig` (which dropped 163 → 109 B accordingly).

## Lessons

- **`SUPPORTS_ALARMS` is the control-engine switch on AVR, not a buzzer flag.**
  `INCLUDE_CONTROL_ENGINE` is `INCLUDE_ALARMS || INCLUDE_RELAY_OUTPUT`
  (`control_types.h`), so disabling alarms removes the entire Rules/Actions engine
  (−16.4 KB / −455 B — grew with the standalone arena tables in #296). The physical
  buzzer is a separate pin (`BUZZER_PIN`).
- **`CLI_BUFFER_SIZE` is the biggest single RAM lever** (−852 B for 820→512),
  larger than any feature — at the cost of max command / JSON-import length.
- **`MAX_INPUTS` is the cleanest scaling knob** (~110 B/input), confirming the
  PR #144 estimate.
- **Not every disabled feature is a RAM ceiling.** `REALDASH` costs +36 B — it's
  off on mega by *choice*, not necessity. `FRAMED_TRANSPORT` (+1,691 B), `ELM327`
  (+301 B), and `TEST_MODE` (+238 B) are genuine ceilings (each exceeds the 90 B
  headroom); `SD_LOGGING` can't even link without added `lib_deps`.
- **ArduinoJson/SD are flash + heap costs, not static-RAM drivers** — consistent
  with the PR #144 finding; the static-RAM drivers are the CLI buffers and the
  input array.
